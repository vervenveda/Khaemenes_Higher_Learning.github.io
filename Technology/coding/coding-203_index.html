Module 1 — Problem Decomposition & Pseudocode 2.0

Here you’ll practice breaking big ideas into smaller steps and writing structured pseudocode.

1 — From Messy Idea to Clear Plan

Every project starts as a messy idea. Decomposition means:

  • Taking a big problem and slicing it into smaller pieces.
  • Focusing on one tiny step at a time.
  • Writing down the journey in clear, ordered steps.

You are learning to think like an architect of code.

2 — Inputs → Process → Outputs

Many problems can be described as:

  • Inputs — What information do we start with?
  • Process — What steps will we take?
  • Outputs — What should the result look like?

Example: “Homework tracker”

  • Inputs: subject, due date, isDone?
  • Process: add tasks, mark them done, sort by due date
  • Outputs: list of tasks, “all done!” message

3 — State Buckets

State is what your program needs to remember while it runs.

  • Score in a game.
  • Which question the quiz is on.
  • Which screen the user is looking at.

We often group state into buckets like:

  • Player bucket — name, score, lives
  • UI bucket — current screen, selected tab
  • Data bucket — tasks, questions, inventory

Module 2 — Core Algorithm Patterns

Now you’ll learn some reusable patterns that appear in almost every program.

1 — What Is an Algorithm Pattern?

An algorithm is a list of steps to solve a problem.

A pattern is a shape those steps repeat over and over in many programs.

  • Count how many things match a rule.
  • Find the biggest or smallest value.
  • Filter a list to keep only good items.

2 — Accumulate (Sum & Count)

The accumulate pattern uses a variable to build up an answer:

total = 0
for each number in numbers:
    total = total + number

We can also count:

count = 0
for each student in students:
    if student.passed:
        count = count + 1

3 — Search, Filter, and Map

  • Search — find the first thing that matches a rule.
  • Filter — keep only items that pass a test.
  • Map/Transform — change each item into a new shape.
# Search
for each item in items:
    if item matches rule:
        return item

# Filter
goodItems = []
for each item in items:
    if item matches rule:
        add item to goodItems

# Map
newList = []
for each item in items:
    add transformed(item) to newList

Module 3 — State Machines & Multi-Step Flows

Here you’ll learn to describe apps as states and transitions instead of chaos.

1 — What Is a State Machine?

A state machine is a way to describe:

  • Which situation (state) the system is in now.
  • What events cause it to change to a new state.

Example: a simple game might have states:

  • START → PLAYING → PAUSED → GAME_OVER

2 — States and Events

Think in pairs:

  • State — “where we are now” (e.g. HOME_SCREEN).
  • Event — “what just happened” (e.g. “user clicked Start”).

Example flow:

state = "HOME"

if state is "HOME" and event is "click start":
    state = "PLAYING"

if state is "PLAYING" and event is "lose all lives":
    state = "GAME_OVER"

3 — Multi-Screen Apps as State Machines

Even simple apps can be drawn as state machines:

  • HOME — show buttons for “New”, “Open”, “Settings”
  • FORM — user fills out a form
  • THANK_YOU — show a success message
HOME --(click "New")--> FORM
FORM --(submit form)--> THANK_YOU
THANK_YOU --(click "Home")--> HOME

This style will help a lot when you design real apps later.

Module 4 — Debugging 2.0: Strategy & Mindset

Debugging is not just fixing errors — it’s learning how to investigate.

1 — Types of Bugs

Common bugs include:

  • Syntax bugs — the code is written in a way the computer doesn’t understand.
  • Logic bugs — the code runs but does the wrong thing.
  • Off-by-one bugs — loops that go one step too far or not far enough.

2 — Debugging Steps

Good debuggers:

  • Reproduce the bug on purpose.
  • Read error messages carefully.
  • Check one small area at a time.
  • Use logs or prints to see what the program is doing.

3 — Tracing & Invariants

Tracing means walking through the code step by step and writing down how the state changes.

An invariant is something that should always be true (for example, “score is never negative”).

If an invariant breaks, you’re very close to the bug.

Module 5 — Mini Project Planning

Now you’ll design tiny project blueprints that prepare you for real code in 301.

1 — Why Plan Before Coding?

Planning helps you:

  • Catch problems early, before they’re buried in code.
  • Stay focused on the goal, not just random features.
  • Explain your idea clearly to friends, teachers, or teammates.

2 — Project Blueprint Sections

A tiny blueprint might include:

  • Title — name of the project.
  • One-sentence goal — what it does for the user.
  • Inputs — what data it needs.
  • State buckets — what it must remember.
  • Main flows — typical user journeys.

3 — Example Blueprint: Quiz Engine

Title: Tiny Quiz Engine
Goal: Let the user answer a short quiz and see their score.

Inputs:
  - List of questions (text + choices + correct answer)
  - Player name (optional)

State buckets:
  - currentQuestionIndex
  - score
  - hasFinished

Main flows:
  - Start → show question → choose answer → next question
  - After last question → show score → offer restart
